**License [verified]**: GPL-3.0 (GitHub license detection; `COPYING`/`LICENSE`), with BSL/BSD/LGPL/MIT/Unlicense notices for bundled libraries. https://api.github.com/repos/simulationcraft/simc , https://github.com/simulationcraft/simc
- Shelling out: the GNU GPL FAQ treats "pipes, sockets and command-line arguments" as communication between separate programs; two programs communicating "at arm's length" are not one combined work. A Python tool that runs `simc` as a subprocess and reads its JSON output is therefore not itself bound to the GPL [inferred from https://www.gnu.org/licenses/gpl-faq.html ; see also https://ifross.org/en/program-forks-gpl-licensed-program-system-or-vice-versa-call-derivative-work ]. Distributing the binary alongside the tool would carry GPL source-offer obligations; the tool is single-user, so this is moot.
- Embedding SimC's data files (spell dumps, `*.inc`) in this repo: those files are generated from Blizzard's own game data ("SimC is built using game tables and game data directly provided via Blizzard's CDN" https://raw.githubusercontent.com/simulationcraft/simc/midnight/SpellDataDump/README.md). Whether a re-encoded table of cooldown/charge numbers is a GPL "covered work" or Blizzard-owned data is a legal question, not a technical one [inferred]; the safe pattern is to generate a derived JSON on the user's machine from a local checkout/binary, keep it in `data/` (already git-ignored), and ship only the generator plus a small test fixture. Not legal advice.

**Talents [verified]**
- `talents=` "accepts Blizzard's in-game generated talent export hash, from either the talent UI export or the Simulationcraft addon" (e.g. `talents=CEkAAAAAAAAAAAAAAAAAAAAAAYAzMzmxMzMmZmMmZAAAAAAAzyDMmtZYmxyMzYZm5BmZWmZWGjBWmFzYY200wMjhNAAAAAAAAmZwAAAAwA` in the MID2 Havoc profile).
- Alternatives that avoid the hash: `class_talents=`, `spec_talents=`, `hero_talents=` — "`/` delimited list of pairs of talent:rank … either the Tokenized Name or the TalentID, i.e. `19979:1/shadowfiend:1`"; "You must use TalentID for any talents that share a name"; `hero_talents=<tree token>` enables a whole hero tree. https://raw.githubusercontent.com/wiki/simulationcraft/simc/Characters.md (section "Talents")
- Midnight adds `omnium_talents=` (option registered at `engine/player/player.cpp` line 13270; `omnium_talents=136822:1/136819:1/…` in the MID2 profile). https://raw.githubusercontent.com/simulationcraft/simc/midnight/engine/player/player.cpp
- What "TalentID" means in code (`parse_traits`, player.cpp lines 2987–3080): a bare number is looked up with `trait_data_t::find(entry_id)` whose parameter is `trait_node_entry_id`; a number prefixed with `s` is a spell id (`find_by_spell`); otherwise the tokenized name. So **TalentID = TraitNodeEntry ID**. https://raw.githubusercontent.com/simulationcraft/simc/midnight/engine/dbc/trait_data.hpp (struct fields `tree_index, id_class, id_trait_node_entry, id_node, max_ranks, req_points, id_trait_definition, id_spell, …, id_sub_tree, node_type`)
- Tree enum (`engine/sc_enums.hpp` line 1413): `talent_tree { INVALID=0, CLASS=1, SPECIALIZATION=2, HERO=3, SELECTION=4, MAX=5, EXPANSION=6 }`; `tree_index` is the first column of `engine/dbc/generated/trait_data.inc` ("Player trait definitions, wow build 12.1.0.69933", 3,435 rows). https://raw.githubusercontent.com/simulationcraft/simc/midnight/engine/sc_enums.hpp , https://raw.githubusercontent.com/simulationcraft/simc/midnight/engine/dbc/generated/trait_data.inc

**What WCL exposes, and does it map? [verified from this project's own `data/cache`]**
- `CombatantInfo` events (already fetched by `collect_data.py` as `cinfo_<fid>`) contain: `specID`, `gear[]` = `{id, quality, icon, itemLevel, bonusIDs[], permanentEnchant?, temporaryEnchant?, gems[{id,itemLevel,icon}], setID?}` (18 slots; 7–9 items carry `permanentEnchant`, 3–5 carry `gems`, 1–2 carry `temporaryEnchant` in a sample of 24 raiders), `talentTree[]` = `{id, rank, nodeID}` (73–81 nodes per player), `talents: []` (empty legacy field), `pvpTalents`, full stat block, `expansion: "dragonflight"` (format label), `faction`. No race, no professions, no crafted-stat modifiers, no talent export string. WCL docs list only `talentTree`, `talentRows`, `talentPoints` as talent fields. https://www.warcraftlogs.com/scripting-api-docs/warcraft/interfaces/RpgLogs.CombatantInfoEvent.html
- WCL's DamageDone/Healing **table** entries (also already cached) carry `gear[]` with `slot`, `permanentEnchant`, `permanentEnchantName`, `gems`, `bonusIDs`, `setID`, `itemLevel`, `name` — but `talents: []`. Talents must come from the CombatantInfo event. WCL staff on per-pull gear: "You want Report → Table API with data type of Summary." https://forums.combatlogforums.com/t/apiv2-access-to-character-gear-per-pull/11180
- **Cross-check of ids** (decisive): WCL `{"id":112839,"rank":1,"nodeID":90929}` (Vengeance DH) ↔ `trait_data.inc` row `{ 1, 12, 112839, 90929, … "Remorseless" }`; six further sampled pairs (117758/95149, 134253/99823, 134271/108722, 136500/110010, 136501/110011, 136810/109450) all match `id_trait_node_entry`/`id_node`. So **WCL `talentTree[].id` is exactly SimC's TalentID, and `nodeID` is `id_node`.** The raw combat-log format is the same triple `(nodeId, entryId, rank)`. https://wowcoach.gg/docs/combat-log/combatant-info
- Splitting by tree for `class_talents=` / `spec_talents=` / `hero_talents=` / `omnium_talents=` is a lookup of `tree_index` in `trait_data.inc`: e.g. 112839 → tree 1 (class), 134271 "Felblade" → 1, 136810 "Harness the Cosmos" → 3 (hero, sub-tree 124), 134253 → 4 (hero-tree SELECTION node, no spell), 136822 "Rune of Unleashed Fire" → 6 (EXPANSION = omnium). WCL's `talentTree` does include the 136xxx/137xxx entries [verified in cache]. Rank comes from WCL `rank`. Whether SimC needs the SELECTION node or infers the hero tree from `hero_talents=` entries must be tested once with a real binary [inferred; `enable_hero_tree` exists in player.cpp].
- The Blizzard export string is a custom-base64 bitstream (spec id, tree checksum, per-node selections in tree order) documented in `Blizzard_ClassTalentImportExport.lua` and decoded by SimC in `parse_traits_hash`; regenerating it from WCL data would need the node ordering. Unnecessary given the id-list options. https://warcraft.wiki.gg/wiki/Dragonflight_Talent_System , https://warcraft.wiki.gg/wiki/API_C_Traits.GenerateImportString
- Gaps to fill from config: `race=` (racials; not in WCL — keep a per-player override file, default per class), `spec=` token from `specID` (a 40-row table), class token from the WCL actor `type` (`DemonHunter` → `demonhunter="Name"`), `role=` from the existing role inference, `level=90`. Crafted items: WCL has no `crafted_stats`; use `ilevel=<itemLevel>` on every line to pin item level regardless of bonus-id decoding, and accept that crafted secondary stats may be wrong [inferred]. `temporaryEnchant` arrives as an id; SimC's `temporary_enchant=main_hand:<token>` wants tokens — map or drop [inferred].

So `sim.players[0].collected_data.dps.mean` is the headline DPS and `stats[i].num_executes.mean` is the average number of executes **per iteration**.
- `stats[]` (per action, only with `report_details`): `id` (spell id), `spell_name`, `item_id` (trinkets), `name` (action token), `school`, `type` (damage/heal/absorb), `resource_gain`, `num_executes {sum,count,mean}`, `compound_amount`, `total_execute_time`, `portion_aps`, `portion_apse`, `portion_amount`, `actual_amount`, `total_amount`, `total_intervals` (only if `num_executes.mean > 1`), `num_ticks`, `num_tick_results`, `total_tick_time`, `num_refreshes`, `num_direct_results`, `direct_results{hit/crit/…: {actual_amount,total_amount,…}}`, `tick_results{}`, `children[]`.
- `buffs[]`: `name`, `spell_name`, `spell` (id), `item{id, ilevel}`, `start_count`, `refresh_count`, `interval`, `trigger`, `uptime` (mean %), `benefit`, `overflow_stacks`, `overflow_total`, `expire_count`, `default_value`, `stack_uptime[]`.
- `gear{slot: {name, encoded_item, ilevel, stats{…}}}`.

**Which fields give the baselines**
- Expected casts per minute of ability X for this player/gear/talents: `stats[X].num_executes.mean / (collected_data.fight_length.mean / 60)`; with `fixed_time=1 vary_combat_length=0` the fight length is constant. `total_intervals.mean` is the mean gap between executes (a cast-cadence baseline). Pet actions are under `stats_pets`. Precombat casts are executed in the sim and are counted in `num_executes` [inferred] and listed in `action_sequence_precombat`.
- Expected buff uptime: `buffs[B].uptime` (percent); `benefit` for "was the buff up when it mattered".
- `html=` produces the human-readable report; `output=` the text one; `calculate_scale_factors=1` adds `scale_factors`/`scale_factors_all`/`scale_deltas` per player (StatsScaling wiki page exists; Raidbots warns stat weights are easy to misuse: https://support.raidbots.com/article/66-beware-of-stat-weights ).
- No sample JSON is checked into the repo; `tests/` and `profiles/CI.simc` exist but the CI writes `json=/dev/null`. To obtain a fixture, run the binary once on a MID2 profile [verified listing; inferred plan].

List operators `& | -`.
- Output is the same block format as the dumps (the dumps *are* `spell_query` output).

**Batch extraction for ~1000 ids [inferred from the above]**: do not run 1000 queries. Either (a) parse the 13 class dump files (+ `nonclass.txt` for trinket/consumable spells) straight from the git checkout — ~18–33 MB of text, trivial to parse in Python into `{id: {name, class, cooldown_ms, gcd_ms, charges, charge_cd_ms, category, category_cd_ms, cast_ms, duration_ms, school, cost, attributes[], affecting[], talent_entry{tree,row,col}}}` — or (b) run `simc spell_query="spell.class=<class>"` per class if a binary is available (13 invocations). Cooldown/charges/GCD for any id are fully offline. A derived JSON limited to the ~1–3k spells the raid actually casts would be well under 1 MB (uncompressed) [inferred].

**Edge cases the oracle exposes but does not solve**: haste-scaled cooldowns/charges are not a single number (WoWAnalyzer notes spells "cast while already marked as on cooldown … probably either has multiple charges, can be reset early, cooldown can be reduced, … the Haste is too low" https://raw.githubusercontent.com/wiki/WoWAnalyzer/WoWAnalyzer/Abilities.md ); talents that add charges or cut cooldowns appear only as `Affecting Spells`/`Category` references whose effect values live in the *talent's* block; procs that reset cooldowns are invisible in the combat log. Category cooldowns (shared) are explicit. So the oracle gives a **static** cooldown, charges, GCD and cast time per spell id, plus pointers to every modifier — enough for "possible casts ≈ 1 + floor((fight − first_cast)/cd) × charges" with a tolerance band, not for exact per-talent numbers [inferred].

**License/size**: see §1 — generated from Blizzard CDN data; regenerate locally rather than committing dumps; total dumps ≈ 90 MB with PTR twins, ≈ 18 MB for live class files [verified sizes].

## 6. Integration options

Shared prerequisite for (a) and (b): a `simc` binary (self-built CLI, or `docker run simulationcraftorg/simc …`) and a profile generator `wcl_to_simc(combatant_info, actor, cfg) -> str` that emits:
```
# report <code> fight <id> pull <n>
demonhunter="Omess"
level=90
race=blood_elf                # from config/simc_players.json, not WCL
spec=havoc                    # from specID 577
role=attack
class_talents=112839:1/…      # WCL talentTree ids with tree_index 1
spec_talents=…                # tree_index 2
hero_talents=…                # tree_index 3 (+ test whether tree_index 4 node is needed)
omnium_talents=136822:1/…     # tree_index 6
head=,id=271537,bonus_id=13692/13698/13750,gem_id=240983,enchant_id=8017,ilevel=334
…
optimal_raid=1
default_actions=1
fight_style=Patchwerk
max_time=312 vary_combat_length=0 fixed_time=1
desired_targets=1
target_error=0.5              # or iterations=2000

```
Run: `simc <profile>.simc` (options may also be passed as CLI args). Cache by `sha1(sorted gear lines + talent lines + spec + fight-length bucket + fight_style + desired_targets + simc build id from json.version/dbc.live.build_level)`.

**a) Sim vs actual DPS** — feasibility: yes; value: low–medium; effort: **M** (given the generator); risks: misleading numbers.
- Method: `collected_data.dps.mean` vs WCL `amount / active or total time` from the existing damage table. Match `max_time` to the kill duration (`vary_combat_length=0 fixed_time=1`), `desired_targets` to the boss's steady target count, `Patchwerk` or `CastingPatchwerk`; `optimal_raid=1` mirrors a full raid; disable buffs the raid lacks with `override.*=0`.
- Caveats (all real): Patchwerk has no movement, adds, downtime, deaths, target swaps, intermissions or externals; sims assume a robot — forum reports for straight single-target sit around 88–98 % of sim (Warrior "131–133k sim vs 116–123k real", "on a training dummy … less by like 10 %", "give or take usually 2 %"), with movement/RNG/missing Windfury/augment runes as reasons, https://us.forums.blizzard.com/en/wow/t/how-you-sim-vs-your-actual-dps/1669898 ; other threads show 65–75 % on mechanics-heavy bosses (summaries of https://us.forums.blizzard.com/en/wow/t/raid-sim-vs-real-time-dps/2021109 and https://us.forums.blizzard.com/en/wow/t/my-st-raid-dps-30k-below-sim-plz-help/1594556 , not fetched in full [inferred]). No authoritative "x % of sim is normal" rule exists in the sources found; the community position is "sims optimise gear, logs judge play" (https://koroboost.com/guide/midnight-dps-sims-guide [inferred from summary]). Raidbots/Archon: no public "sim vs log" comparison feature was found; Raidbots' own help stresses sims are theoretical maxima and warns about stat weights. https://support.raidbots.com/article/66-beware-of-stat-weights , https://support.raidbots.com/article/55-smart-sim
- Further caveats: the sim uses pull-time gear/talents (good, that's what WCL gives) but not the raid's actual buff set or the player's deaths; item level of crafted items may decode wrongly without `crafted_stats`; race is unknown; `Devourer`/Midnight specs may be marked experimental (`allow_experimental_specializations`).
- Verdict: worth showing only as a **per-player trend relative to their own sim across nights on the same boss** (e.g. "76 % → 84 % of sim"), never as a cross-player ranking. The WCL parse percentile already does the cross-player job.

**b) Baseline casts-per-minute and buff uptime** — feasibility: yes; value: **high** for DPS and tanks, none for healers; effort: **M–L**; risks: name/id mapping and talent-dependent ids.
- From the same JSON: `stats[i].id` (spell id) + `num_executes.mean` ÷ fight minutes → expected casts/min; `buffs[i].spell` + `uptime` → expected uptime. Compare with WCL `Casts` events (already fetched for the first-death window; extend to whole fight per player — one `events(dataType: Casts, sourceID:…)` per fight, batched like the consumable query) and `Buffs` events (`targetID`, compute uptime from applybuff/removebuff pairs).
- Pitfalls: (1) match on **spell id, not name** — WCL and SimC both carry ids; SimC `stats[].name` is a token (`eye_beam`) and `spell_name` the display name; (2) one action may show up as several ids in the log (rank/override spells such as Eye Beam 198013 vs 198030 damage id; talents that *replace* spells — `trait_data.inc` has `id_replace_spell`/`id_override_spell`, and the dump has `Replaces`) — normalise via the dump's `Replaces`/`Triggered By` or a small alias table; (3) procs and RNG make single-fight counts noisy — report ±1 cast tolerance and only for abilities with ≥ 3 expected casts; (4) precombat casts (`action_sequence_precombat`) happen before the WCL pull timestamp — the existing `PREPOT_BEFORE_MS` window logic applies; (5) fight length must be the actual pull length, and *dead time* (player death → end) should be subtracted before comparing; (6) multi-target bosses: rerun with `desired_targets` or accept a wider tolerance; (7) sim `num_executes` of channels/auto-attacks are not "casts" — filter to `type=damage/heal` foreground actions with GCD (dump `GCD` field) [all inferred]. WoWAnalyzer's mature equivalent uses hand-maintained per-spec `cooldown`/`charges` tables and an 80 % recommended cast-efficiency threshold — the sim replaces the hand tables. https://raw.githubusercontent.com/wiki/WoWAnalyzer/WoWAnalyzer/Abilities.md
- Output in the dashboard: per player per kill/best pull, a short table "Ability · you · sim expects · Δ" limited to the 6–8 highest-`portion_aps` abilities plus major cooldowns, and "Buff · your uptime · sim uptime" for the top buffs by `benefit`/`uptime`. Small, table()-based, fits the size budget.

**c) Spell-data oracle only (no simulations)** — feasibility: yes; value: **medium–high across every spec, including healers**; effort: **S–M**; risks: talent modifiers and haste.
- Build `data/spell_oracle.json` from the dumps/`spell_query` (§4) for the ids seen in `data/abilities_seen.json` plus every id in the players' `Casts` events; per id keep cooldown, charges + recharge, category + category cooldown, GCD, cast time, duration, school, `Reset Cooldown on Encounter End`, and the ids in `Affecting Spells`/`Category`.
- Generic analyses that then work for all 40 specs: cooldown usage efficiency ("possible casts" from cooldown/charges vs actual, with the WoWAnalyzer 80 % convention), major-cooldown timing (first use delay, time wasted at full charges), GCD downtime / "always be casting" (share of fight where no GCD-triggering cast is active, using GCD/cast time and haste from the CombatantInfo stat block), interrupt/dispel cooldown usage, and for healers: cooldown usage of healing CDs and downtime — none of which SimC's healer coverage could provide.
- Coverage limits: talents that lower cooldowns or add charges (e.g. `A Fire Inside` on Immolation Aura) must be applied by hand — the oracle tells you *which* talent ids matter, and the player's `talentTree` tells you whether they have it; haste-scaled charges/cooldowns need a per-spell flag; category (shared) cooldowns are explicit; proc-based resets are invisible in logs — present efficiency with a band, and flag abilities whose oracle data is ambiguous instead of scoring them [inferred].

**d) Stat weights / gear advice** — out of scope. `calculate_scale_factors=1` multiplies run time by (number of stats × iterations), gear advice belongs to Raidbots/Top Gear which the players already use, and Raidbots itself warns that stat weights are widely misused (https://support.raidbots.com/article/66-beware-of-stat-weights). It also has nothing to do with *log* analysis.

**Run time and volume [inferred; no benchmark source found]**: the default is `target_error=0.2` up to 1 M iterations (wiki); Raidbots uses staged 1 % / 0.2 % / 0.05 % errors and notes ~100–200 iterations suffice at 1 % (https://support.raidbots.com/article/55-smart-sim). For cast/uptime baselines a 0.5–1 % DPS error is irrelevant next to the 10–30 % sim-vs-real gap, so `target_error=1` or `iterations=1000–2000` is plenty; expect seconds, not minutes, per single-actor sim on a modern multi-core desktop, and sub-minute for `target_error=0.2` on most specs (estimate — measure once with `sim.statistics.elapsed_time_seconds`). Volume: 20 raiders × distinct (gear, talents, fight-length bucket) combinations per week is typically 20–60 sims because gear changes weekly and fight lengths can be bucketed to 30 s; with the cache key above, a weekly "one sim per raider at current gear per boss-length bucket" batch is enough, run in the background by the existing systemd timer. Do not sim per pull.

## 7. Verdict

Ranked for a Python tool that is offline-testable, keeps the HTML small and is run by one person on Arch:

1. **(c) Spell-data oracle first.** Smallest effort, covers all specs and roles (the only option that helps healers), needs no binary at build time (parse dump files from a shallow git checkout, or `spell_query` once if a binary exists), and its output is a plain JSON that becomes a committed **test fixture** (a few hundred ids). Feeds generic cooldown-efficiency / downtime sections that fit the existing `table()`/`kpis()` patterns.
2. **(b) Sim-derived cast and uptime baselines.** Highest ceiling for DPS/tank feedback without hand-written per-spec rules; medium–large effort (profile generator with the tree-index split, id normalisation, whole-fight Casts/Buffs fetch, cache). Needs the `simc` binary at build time; a weekly batch is enough. Ship after (c) proves the WCL-side cast/uptime plumbing.
3. **(a) Sim vs actual DPS** as a small add-on to (b): same JSON, one number, shown only as the player's own trend with the Patchwerk caveat spelled out in the UI.
4. **(d) Stat weights**: no.

**Binary dependency and graceful degradation**
- Locate via `SIMC_BIN` in `.env` → `shutil.which("simc")` → optional Docker fallback (`docker run --rm -v profile:/p simulationcraftorg/simc /p/x.simc json2=/p/out.json`); record `sim.version`/`dbc.live.build_level` in the cache key so a rebuilt binary invalidates results.
- Absent binary: skip the sim sections and render `empty_state("Sim baselines", "simc not found — build it from https://github.com/simulationcraft/simc (midnight branch, -DBUILD_GUI=OFF) and set SIMC_BIN")`; the oracle-based sections still render. Build never fails because of SimC.
- Tests: never invoke `simc`. Commit (i) one trimmed `json2` output for a MID2 profile (players[0] with `collected_data.dps`, ~10 `stats[]`, ~10 `buffs[]`, `options`) and (ii) the oracle JSON subset; unit-test the profile generator against the fixture CombatantInfo (the current fixtures strip `gear`/`talents` in `tests/make_fixtures.py` `_TABLE_DROP`/`_CINFO_KEEP` — a new slim fixture must keep `gear` and `talentTree` for one or two players), the tree-index splitter (against a committed 20-row slice of `trait_data.inc`), the id normaliser and the comparison maths. Mark any live-binary test `skipif(not SIMC_BIN)`.
- Size: only per-player deltas (ability, actual, expected) go into the payload — tens of bytes per row, well inside the 10 MB Discord ceiling.
- Repo hygiene: generated profiles, `json2` outputs and the oracle JSON live under `data/` (ignored); SimC's data files are not vendored (§1 license note); the SimC checkout path/binary path are user config.
