## Per-player combat analysis — Phase 1 ("mine the cache": the per-player card)

**Plan:** `docs/plans/2026-10-01-player-analysis-phase1-plan.md` (the orchestrator's working plan, tasks T1–T9; it refines the design's
§8 Phase 1 rows P1.1–P1.9, P1.V, P1.D of `docs/plans/2026-09-25-player-analysis-design.md`). One sub-agent per task per `CLAUDE.md` §0.
Source of these notes: the eight Phase 1 entries (T1–T8, 2026-10-01/02) in `.claude/CHANGES.md` written by the implementing agents, plus the
T9 verification run.
`[DECISION]` The plan's §4 owner decisions were adopted with their defaults: `ish` (E9) dropped; wipe-cutoff constants as pinned; D5 deferred

### T1 — Analysis core: `PM_COLS`, wipe cutoff, event digest, tank mitigation, collector hooks — `analysis/`, `collect_data.py`, `build_dashboard.py`

- `[ADDED]` `analysis/wipe.py`: `wipe_cutoff_s(kill, duration_s, death_times, wipe_called_s)`. It returns `wipe_called_s` when WCL set it, and
  `None` on kills. Otherwise it looks for the longest run of deaths with gaps ≤ `WIPE_CASCADE_GAP_S` (10 s) that has at least
  `WIPE_CASCADE_MIN_DEATHS` (3) deaths and ends within `WIPE_TAIL_S` (20 s) of the pull end. The cutoff is the **first death of that run**,
  which still counts. Fixture fight 8 gives 92.5 s; fights 2, 7 and 9 give `None`. Stdlib only.
- `[ADDED]` `analysis/mitigation.py`: `load_tank_mitigation()`, `spec_label(cls, token)` ("Protection Paladin" / "Protection Warrior" only for
  shared tokens), `am_ids_for(spec_token, cls=None)` (a shared token without a class returns the union), `parse_buffs()`, and
  `digest_events(events, participants, spec_ids, cutoff)`. The digest gives one entry per participant
  (`dtk, hits, hits_buffs, dodge_parry_miss`), and tanks also get `am_up, amw_num, amw_den, mit_num, mit_den`.
  It also defines the `TANK_BUFFS_SEEN` counter and the constants `CONNECTED_HIT_TYPES = {1,2,4,5}`, `DODGE_PARRY_MISS_TYPES = {0,7,8}` and
  `AM_BUFFS_MISSING_MAX = 0.30`. Imports: stdlib + `specs` + `path` only.
- `[ADDED]` `analysis/player_metrics.py`: `PM_COLS` (23 columns:
  `act dps hps dth fd alv avh avm dtk dtps prep pot hs ir ds ilvl rp bp oh mit am amw gap`), `COL`, `trim(vec)`, `role_of()`, and
  `player_metrics(pull, avoidable, ignored, gear_gaps=None)`. `hps`/`oh` are filled for healers only and `mit/am/amw` for tanks only, with the
  30 % aura-data rule. The cutoff applies to `dth/avh/avm/dtk/dtps/mit/am/amw` (`seconds <= cutoff`) but not to `fd/alv`.
- `[ADDED]` `collect_data.py`:
  - event dicts gain `buffs`, `mitigated`, `hit_type`, `blocked`;
  - table rows gain `overheal`;
  - new `_gear_rows()` + `gear_from_bundle()` → `{label: [[slot, ilvl, enchant_id_or_0, n_gems, item_id], ...]}` (damage row gear by `slot`,
    then the healing row, then cinfo gear by index);
  - `get_parses` stores `bdps`/`bhps` (`bracketPercent`) and `spec`;
  - `collect()` adds the pull keys `wipe_cutoff_s`, `player_events` and `gear`.
- `[ADDED]` `build_dashboard.py`:
  - `write_tank_buffs_seen()` writes `data/tank_buffs_seen.json` (top 25 buff ids per tank spec, with hit counts). It writes nothing when no
    tank hit carried aura data.
  - `tank_mitigation_warnings()` (called from `validate_config()`) warns about unknown spec keys and about configured ids never seen on that
    spec's tanks in the build.
- `[ADDED]` `config/tank_mitigation.json` + `.example.json`: Vengeance, Protection Paladin, Protection Warrior, Blood, Guardian, Brewmaster.
- `[CAVEAT]` Only the four Vengeance ids are verified (all seen on the fixture tanks: Demon Spikes 203819 on 1,767 hits, Fiery Brand 207771,
  Metamorphosis 187827, Soul Barrier 263648). The other five specs' ids are TWW-era guesses. The build prints
  `tank_mitigation.json: <spec> ids never seen in any <spec> tank's buffs in this range: ...` once a real build has such a tank.
- `[DECISION]` Payload deviation flagged by T1: `parses` is emitted as stored, so the new `bdps`/`bhps`/`spec` keys reach the browser
  (+157 B base64 per pull on the fixture, kills only). Contract C pins them inside `parses[label]`.
- `[DECISION]` Pinned deviations: `dtk` and `am` do not exclude `_ignore` / avoidable abilities, because the digest runs in `collect_data`, which
  does not load `avoidable.json`. Friendly pets as damage sources count as enemy hits (same as `aggregate_damage`). A tank spec with no config
  entry gets `mit_*` but no `am_*` keys, and one console note per spec label per process.
- `[CAVEAT]` The fixture cannot exercise these cases, so they are tested synthetically only: a set `wipe_called_s`, blocked hits, non-Vengeance
  tanks, the cinfo-only gear fallback, and the 30 % rule.

### T2 — Gear checks — `analysis/gear.py`, `config/gear_checks.json`

- `[ADDED]` `slot_name()`, `roster_rules(gear_by_label, cfg)` → `{"enchant_slots", "gem_slots"}`, `gear_report(rows, rules, cfg)` →
  `{"ilvl", "gaps", "n_gaps"}`, `latest_gear(pulls_by_label)`, `load_gear_checks()` (defaults when the file is missing or invalid), `DEFAULTS`.
- `[ADDED]` Gap strings: `"head: no enchant"`, `"ring 2: empty socket"`, `"wrist 19 ilvl below your average"` (item ilvl ≤ mean − `low_slot_gap` 15).
  They are in slot order; within a slot the order is enchant, then socket, then low ilvl. Shirt (3), tabard (17), and rows with item id 0 or ilvl 0
  are ignored everywhere.
- `[ADDED]` `config/gear_checks.json` + `.example.json`: `enchantable` / `socket_slots` = `"auto"` (roster-majority rule), `majority` 0.5,
  `skip_slots` [3, 17], `low_slot_gap` 15, `slot_names`.
- `[DECISION]` The majority rule is **strict** (`enchanted / non-empty > majority`), not the plan's `>=`. On the fixture the off hand is
  4 enchanted out of 8 non-empty (exactly 0.5), and slot 16 must not be required. Fixture result: enchant slots {0,2,4,6,7,10,11,15}, gem slots {1,10,11}.
- `[CAVEAT]` `gear_report` returns `ilvl: None` (not an int) when a player has no usable rows.

### T3 — Payload: `pm` / `pmcols` / `wc` / `av`, ilvl in `dd`/`hd`, Players-tab block, `cfg.named` — `dash/payload.py`, `dash/page.py`

- `[ADDED]` `_death_payload(d, first, avoid=None, tank_spec=None)`:
  - new `av` = 1 when the killing blow, or ≥ 50 % of `window_damage` (summed over the full recap), comes from `avoidable − ignored`. It is
    always 0 when the boss has no avoidable list.
  - For a **dying tank**, every recap row gets a 6th element `1/0/null`: an AM id is (or is not) in that event's `buffs`. This is design T7,
    pulled forward from Phase 3.
- `[ADDED]` `pull_payload(..., pm=None)` adds, per pull, `"pm": {label: trim(vec)}` for every participant and `"wc"` (the wipe cutoff).
  `dd`/`hd` rows gain `ilvl` as a 6th element. At boss level it adds `"pmcols": PM_COLS`. There is a shared `_encode(obj, compress)`.
- `[ADDED]` New functions:
  - `gear_rules_for()`;
  - `all_metrics(bosses, avoidable_cfg, gear_cfg=None)`, which also fills each pull's `gap` from `gear_report` against the roster rules;
  - `players_data()` and `players_payload()`, which build Contract E: `{cols, roster, nights, sev, gear, advice, named}`.
- `[CHANGED]` `dash/page.py::build_html`:
  - derives `mode` the same way as `home.py` and computes `pm_by_key` once;
  - emits `<script type='application/gzip+base64' id='data_tabPlayers'>` (plain JSON under `--uncompressed`) inside the Players panel;
  - the `cfg` script becomes `{**specs.role_sets(), "named": mode == "named"}`.
- `[DECISION]` `kc` (interrupt cast counts) is dropped from Phase 1. T3 notes that `kc` never existed in this payload, so there was nothing to remove.
- `[CAVEAT]` The size guard was rewritten:
  - The literal `after ≤ before + 800` per pull misses by **1 B** on the fixture (+801 B/pull). `pmcols` is a per-boss-tab constant, and the
    4-pull fixture charges it as about 80 B per pull.
  - The guard now checks two things: the growth without `pmcols` ≤ 800 B/pull (measured +724), and the growth with it ≤ 850 B/pull.
  - The Players block guard is ≤ 25 KB base64; the fixture block is 3.7 KB.
- `[CAVEAT]` `pm`, ilvl and the parse keys scale with players: 15.5 per pull in the fixture against 23.4 in real builds. Real builds will
  therefore grow by about +1.0–1.1 KB base64 per pull, above the plan's 0.65 KB estimate. That is still well inside the +0.7 MB/month
  budget (see Verification).
- `[ADDED]` Tests: `test_payload_phase1_keys`, `test_death_av_flag_and_tank_recap_flag`, `test_players_payload_block`,
  `test_players_payload_named_and_uncompressed`.

### T4 — Severity engine — `analysis/severity.py`

- `[ADDED]` `compute(bosses, pm_by_key, specs_by_key, cols, named=False)` → `{"sev": {label: {night: [items]}}, "advice": ADVICE, "nights": [...]}`.
  Each item is `[metric, value, baseline, bkind, level, score, tpl, affected, pulls]`; named builds add `rank` ("3 of 12") as a 10th element.
- `[ADDED]` Helpers `aggregate_night`, `baseline`, `tolerance`, `score`; the constants `RULES`, `NOTE_ONLY`, `BANDS`, `SHORT_EXCLUDED`, `ADVICE`.
- `[ADDED]` How an item is scored:
  - **Baseline cascade:** own history (≥ 2 earlier nights of the same type) → role median (≥ 3 others present on ≥ 25 % of the pulls; tanks
    use the co-tank) → band → null.
  - **Watch rule:** `affected ≥ max(3, ceil(0.25·pulls))`.
  - `prepot` is Note-only.
  - Pulls under 60 s are left out of `act/dps_ratio/hps/oh/am`.
  - Support specs are left out of role medians.
  - **Ordering:** level (watch < good < note), then tier, then score descending, then metric.
- `[DECISION]` Choices pinned beyond the plan:
  - Healers get an `hps` item (±8 % relative, higher is better, tier 6) instead of `dps_ratio`; tanks get neither.
  - `prep` and `prepot` have a fixed baseline of 0 with `bkind="band"`, and `prep` is the one band-baselined metric that may be Watch.
  - "Worse beyond tolerance" but below the affected floor → Note.
  - Note-only metrics get score 0 and tier 9.
  - The co-tank baseline has no minimum count.
- `[CAVEAT]` The engine emits every item; the public cap (≤ 3 Watch, ≥ 1 Good) is applied in JS. Imports: stdlib + `specs` only.

**Projection for a real month (140–200 pulls, 23.4 players per pull):**

- The per-player part of the delta (pm, parse keys, ilvl ≈ 654 B/pull at 15.5 players) scales to about 990 B/pull. Adding the per-pull
  constants gives ≈ **+1.0–1.1 KB base64 per pull**, which is +140–220 KB per month.
- The Players block is about 230 B per player-night, ≈ 60–80 KB per build-month.
- Total ≈ **+0.2–0.3 MB/month**, against the **+0.7 MB/month** budget.
- Reference: the 269-pull build `dashboard_2026-08-19_to_2026-10-01.html` (2.24 MB) would grow to ≈ 2.6 MB, still far below Discord's 10 MB.
- `[CAVEAT]` The design's exit criterion "payload per pull ≤ baseline + 0.8 KB base64" holds only if 0.8 KB is read as 819 B, or once the
  per-tab `pmcols` constant is left out (+724 B). Read literally as 800 B it misses by 1 B (see T3).
